# Мерж

Этап 2. Граф — `docs/CONTRACT.md` и `packages/schema/src/merge.ts`. Критерии — `docs/ACCEPTANCE.md`, раздел C.

## Кто что пишет

Владелец нажимает кнопку. Сервер кладёт файл в `data_dir/outbox/` и статус запроса не трогает.

| Кнопка | Файл | Когда можно |
|---|---|---|
| Смержить | `outbox/decisions/<id>.json`, `action: approved` | `awaiting_owner`. Красный CI — только с `accept_risk: true` |
| Отклонить | тот же файл, `action: rejected` | `awaiting_owner` и непустой отзыв |
| На доработку | `outbox/feedback/fb-<id>.json`, `intent: changes_requested` | `awaiting_owner` и непустой отзыв |
| Да, откатить | `outbox/decisions/<id>.json`, `action: revert` | статус запроса `merged` |

Поле `by` ставит сервер: `mr.owner`, а если его нет — `project.owner`. Тело запроса это поле не выбирает. `owner.confirms_merge` в конфиге должен быть `true`.

Чаты в отзыве: по умолчанию отмечены `affected_chats`. В файл попадают только id чатов этого проекта. `sent_to_chats` совпадает с отметками.

## Доставка

`POST /api/sync/apply` читает outbox и пишет `merge_requests/`. Пока вызова не было, статус на диске тот же, что до клика.

Последнее действие по полю `at` побеждает. Чужой `by` и несовпавший `head_sha` доставку пропускают. Если запрос уже `approved`, а `head_sha` решения другой — переход обратно в `awaiting_owner` с причиной `head_sha_changed`.

Допущение этого среза: живого бота нет. Один вызов синка на демо делает шаги главного и исполнителя подряд.

1. `approved` — решение владельца.
2. `delivered` — «доставлено на бокс» (роль главного).
3. Бриф `мержи <id> <pr_url>`. Собирается только здесь: статус уже `delivered`, действие `approved`, `by` равен владельцу. Иначе исполнитель не стартует.
4. `merging` — исполнитель получил бриф.
5. `merged` либо `merge_failed` и сразу снова `awaiting_owner`. Текст ошибки остаётся в журнале и виден в модалке.

Откат из `merged`: бриф `откати <id> <pr_url>` требует `mode: revert` (это аргумент брифа, не поле запроса), действие `revert` и `by` владельца.

Журнал каждого шага: `history[{state, at, by, why}]`. Пара вне графа не пишется.

## Режимы

`git`. Ответ даёт `apps/server/src/merge/github-mock.ts`. `fetch` не вызывается, токен не читается. В `pr_url` есть `/mock-fail/` — мерж падает текстом «мок GitHub: мерж не прошёл».

`files`. Поле запроса `files[].path` — относительный путь внутри папки проекта. Нельзя сегмент `.git` (в том числе `.git/hooks` и `.git ` с хвостовым пробелом), `backups.` с хвостовой точкой, `staging/`, имя устройства Windows (`CON .txt` тоже), NUL, «.», пустой сегмент и двоеточие (`note.txt:stream`). Новое содержимое лежит в `staging/<path>`, живой файл — в корне папки. Манифест новых файлов пишется до цикла копирования. Перед заменой байты живого файла пишутся в `backups/<mr-id>/<path>` через временный файл и rename. Перед rename путь ещё раз проверяется на симлинк; на Linux каталог открывается с `O_NOFOLLOW`. Остаток гонки описан в `docs/files-safety.md`. Файла до мержа не было — его имя уже в манифесте, откат такой файл удаляет. Повторный перенос первый снимок не затирает. Обрыв посреди копирования возвращает уже заменённые файлы из снимка и удаляет те, которых до мержа не было. Сбой отката пишется в `fault` и в `history`, на экране виден владельцу и тем же решением не повторяется. Успешный переход снимает `fault`. Ошибка одного запроса не останавливает остальные в том же синке.

## Итерация на демо

«На доработку» после синка пишет в текущую итерацию решение `changes_requested`, добавляет итерацию n+1 и возвращает `awaiting_owner`.

Цитата — текст отзыва. Исправлено — «исправлено по отзыву». Осталось — «осталось проверить». Это заглушка исполнителя, не разбор диффа. Тот же отзыв (текст и `at`) второй раз итерацию не добавляет.
