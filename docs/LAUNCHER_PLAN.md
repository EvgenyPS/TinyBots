## Резюме

1. **Доставка брифа.** Бриф идёт через «главного» бота: главного в проекте или в чате, это задаётся в конфиге. Фиксированного диспетчера нет. Флоу: «Скопировать бриф» → «Открыть чат главного» (`grokbot://…`) → вставить. Очередь по рутине по умолчанию выключена.
2. **Хостинг и стек.** Локальный сервер на `127.0.0.1` (у нас ПК на Windows). Стек: Node.js 20 + TypeScript, Hono, Vite + React на основе v6, npm workspaces, zod-схемы в `packages/schema`, БД нет. Запуск одной командой. Синк бокса и ПК — по одному бандлу `.tgz` с `sha256` в каждую сторону, копирует главный бот.
3. **Записки о статусе.** В конце хода бот пишет в файл короткую записку: что сделал и чего ждёт. Лаунчер её показывает (время обновления; устаревшие — серым). Сама записка бота не будит.
4. **Универсальность.** Проект пойдёт в публичный git, поэтому в коде нет ни ботов, ни путей, ни проектов. Всё задаётся в `config.yaml`, демо-данные вымышленные, секреты лежат только в `.env`.
5. **Мерж.** Подтверждает владелец проекта (у нас это владелец). Автомат: `approved → delivered → merging` (`docs/CONTRACT.md`, §4.5). Мерж привязан к задаче: если она шла в одном чате, мержится и уведомляется только он; пересечения с другими чатами показываются в окне мержа. `merge_executor` стартует только из `delivered`. Откат — через revert-PR или снимок, тоже с «да» владельца.
6. **Проект без git** (у нас Demo Files): вкладка Git скрыта, запрос на мерж работает в режиме «принять изменения в файлах».

## 1. Как бриф доходит до бота

**Что есть на самом деле.** У Grok-ботов нет публичного API для внешнего веба. Бота будит только сообщение (от человека или от другого бота) или его рутина. Запись в файл бота **не будит**.

**Кому уходит бриф.** В конфиге у каждого чата и проекта указан `lead`. Порядок выбора: главный в чате → главный в проекте. Главный сам решает, кому из участников направления передать задачу (через сообщение агенту), и отвечает за итог. Остальных не будят.

**Способы доставки:**

| Способ | Как | Плюсы | Минусы |
|---|---|---|---|
| **1. Копировать → открыть чат** (основной) | «Скопировать бриф» кладёт текст в буфер. «Открыть чат главного» ведёт по ссылке `grokbot://app/v1/agent?id=<id бота>`. Рядом всегда «Если чат не открылся, откройте <имя> вручную». Владелец вставляет бриф и отправляет. | Работает всегда. Будит ровно одного бота. Без выдуманных API. | Один ручной шаг. Ссылка открывается только внутри приложения Grok Bot, а из браузера может не сработать (техпроверка 1, §12). Подсказка с именем видна и когда ссылка есть. |
| **2. Очередь в файлах + рутина главного** (опция, по умолчанию выключена) | Лаунчер пишет `outbox/queue/<task_id>.yaml`, главный забирает задания. Запуск раз в день по cron или по кнопке «Отправить очередь» (это тоже сообщение главному), не чаще. | Задания копятся пачкой, без ручного шага на каждое. | Стоимость заранее не посчитать: каждый запуск — отдельный ход бота, он виден как доля рутин в статистике (техпроверка 3, §12). Задержка до запуска. Доступ к ПК требует одобрения. |
| **3. Своё API или вебхуки** | — | — | Невозможно, в план не входит. |

**Рекомендация:** способ 1 по умолчанию, способ 2 включается в конфиге (`delivery: clipboard | queue`).

**Записки о статусе (человеческим языком).** В конце каждого хода бот пишет короткую записку: что сделал, над чем работает, чего ждёт и какие у него вопросы к владельцу. Записка ложится в файл `status/<bot_id>.json`. Лаунчер читает файл и показывает записку на орбите, в карточке бота и на канбане: «обновлено ЧЧ:ММ». Если записке больше порога часов (по умолчанию 6 ч, настраивается в проекте), она помечается серым и иконкой часов: «устарело». Записка никого не будит. Чтобы бот что-то сделал, нужно сообщение или рутина.

**Где лежат файлы и как они ходят.** Боты работают на общем боксе, сервер на ПК. Поэтому есть две копии одной папки:
- **Бокс:** `<data_dir>/`. Боты пишут сюда записки (`status/`), задачи (`tasks/`), запросы на мерж (`merge_requests/`) и снимки расхода (`usage/`).
- **ПК:** `data_dir` из конфига, у нас `<data_dir>/` (в `.gitignore`). Лаунчер читает только эту локальную папку, а пишет в `outbox/` (очередь, решения по мержу, отзывы).
- **Синхронизация делает главный бот** одним бандлом `.tgz` в каждую сторону (`docs/CONTRACT.md`, `ARCH.md` §4): `sync/box-to-pc.tgz` (tasks, status, merge_requests, usage) и `sync/pc-to-box.tgz` (outbox). В бандле `sync_manifest.json` (path, sha256, updated_at). Итого 2 операции на ПК вместо N. Распаковку делает лаунчер, неизменённые файлы пропускает и не перезаписывает файлы чужого писателя. Каждая операция на ПК требует одобрения доступа. Синхронизация — в конце хода главного, при «Отправить очередь» или по просьбе, и только если манифест изменился. Держится ли одобрение для рутины без участия человека — техпроверка 2 (§12).
- **Свежесть:** в каждом файле есть `updated_at`. Лаунчер показывает «данные на ЧЧ:ММ» (зона из конфига) и кнопку «Синхронизировать», которая собирает бриф главному: «синхронизируй лаунчер».
- **Решение по мержу** вступает в силу только в состоянии `delivered`. Его ставит только главный после синка. Лаунчер ставит `approved` («отправлено, не доставлено»); `merge_executor` из `approved` не стартует (§4.5).

## 2. Хостинг

Локальный сервер на машине пользователя, по умолчанию `127.0.0.1:<port>` (у нас ПК владельца на Windows). Слушает только loopback, наружу ничего не открывается. Десктоп-обёртка (Tauri) появится только по запросу.

**Стек (наше решение, уточнения — `ARCH.md` §1 и `docs/CONTRACT.md`):** Node.js 20 LTS + TypeScript strict. Сервер на **Hono** (`@hono/node-server`), фронт на **Vite + React**, перенос v6 в компоненты. Плюс `zod` для схем и `yaml` для конфига. TanStack Query, инвалидация по SSE и `chokidar` — позже. `simple-git` — с вкладкой Git. Octokit и токен из `.env` — позже.
Репозиторий — npm workspaces. Схемы — `packages/schema` (zod; из них генерируется JSON Schema в `schema/`, один источник типов для server и web). **БД нет:** всё — файлы в `data_dir`. SQLite — только если появится история или статистика больше одного экрана.
Почему:
- Один язык на фронте, сервере и в схемах.
- Кроссплатформенно (Windows, macOS, Linux), без Python и без сборки нативных модулей.
- Hono лёгкий, работает на стандартных Web API, его легко перенести в Tauri или Deno.
- Vite быстрый, React привычен контрибьюторам публичного репо.

**Безопасность** (`ARCH.md` §5, `docs/CONTRACT.md`): слушать только `127.0.0.1`; проверка заголовков `Host`/`Origin` (DNS rebinding) и CSRF-токен на все записывающие роуты; доступ к файлам только внутри путей из конфига (нормализация, запрет `..` и симлинков наружу). Секреты только из `.env`, в API и логи не попадают; gitleaks в pre-commit и CI.

Запуск одной командой: `npx team-launcher` или `npm start`. Команда собирает фронт, поднимает сервер и открывает браузер. Без `config.yaml` открывается мастер настройки.

## 3. Универсальность: конфиг вместо хардкода

### 3.1 `config.example.yaml` (фрагмент)
```yaml
owner: { name: "Alex", confirms_merge: true }        # владелец проекта подтверждает мерж
data_dir: "./data"                                    # очередь, записки, запросы на мерж
delivery: clipboard                                   # clipboard | queue
bots:   # grok_id — id бота для ссылки grokbot://app/v1/agent?id=<grok_id>
  - { id: lead1, name: "Ава",  role: "тимлид",   avatar: "assets/ava.svg", grok_id: "<id>" }
  - { id: dev1,  name: "Бит",  role: "код",      executor_for_merge: true }
  - { id: qa1,   name: "Тэст", role: "Проверка" }
  - { id: rev1,  name: "Рев",  role: "ревизор", paused: false }
projects:
  - id: demo-game
    title: "Demo Game"
    lead: lead1
    owner: owner                                      # единственный, кто подтверждает мерж
    merge_executor: dev1                              # кто выполняет мерж после «да»
    source:
      git: { provider: github, repo: "example/demo-game" }   # или null
      files: { path: "./demo-project" }
    chats:
      - id: dev
        title: "Сборка"
        lead: dev1
        members: [dev1, qa1, rev1, lead1]
        rules: { do: "код, тесты, ревью", dont: "дизайн, посты" }
        context: ["src/main.gd", "docs/ACCEPTANCE.md"]
        economy: { wake: mentioned_only, reply_limit: short }
economy:
  defaults: { wake: mentioned_only, reply_limit: short, max_wakes_per_task: 3 }  # ответ ≤6 строк, бриф ≤8, пробуждений ≤3 (раунд 4)
  stale_after_hours: 6                                                           # серой через 6 ч, настраивается в проекте (раунд 4)
```
Токены, ключи и пути к ним в YAML не пишутся. Они лежат только в `.env`.
`rules.base` (базовые правила владельца, §7) включены всегда и в конфиге не выключаются. Настраиваемые правила — `rules.defaults`, см. `skill/team-token-economy.md`.
Проверки по расписанию задаются в проекте и по умолчанию выключены (раунд 3). Недельный аудит протокола ведёт бот, выбранный в настройках лаунчера (раунд 3). При расхождении правил чата и проекта лаунчер показывает запрос, решение за пользователем (раунд 3).

    sync/          # манифест и бандлы .tgz

  schema/          # сгенерированный JSON Schema (артефакт packages/schema)

### 3.5 Онбординг
1. `git clone`, затем `cp config.example.yaml config.yaml` и `cp .env.example .env`.
2. Первый запуск: если `config.yaml` нет, открывается **мастер настройки**: владелец → боты (имя, роль, аватар) → проекты → чаты, участники и главные → источники (git или папка) → способ доставки → лимиты экономии. Мастер записывает `config.yaml`.
3. Режим «Демо» показывает вымышленный проект без настройки.
4. Мастер проверяет пути и доступ к git и показывает, что вкладка Git будет скрыта, если git нет.

### 3.6 Секреты и `.gitignore`
- Секреты только в `.env` или в системном хранилище ключей. Токен GitHub нужен только серверу и только для чтения (fine-grained, read-only), во фронт он не попадает. Токен с правами записи — предупреждение, Git-вкладка не стартует (`ACCEPTANCE.md` G3).
- Ключ своего бота: в конфиге только имя `api_key_env`; значение читается из хранилища ОС (сервис `tinybots`, учётная запись — это имя), а если записи нет или хранилище недоступно — из `.env`, и в репозиторий, API, логи и фронт не попадает.
- Закрытый канал (0.3.0): отдельная карточка ключа, не ключ модели. Имя `^[A-Z][A-Z0-9_]{0,63}$`. В пульте — описание, заголовок для подстановки (например `Authorization: Bearer`), флаг «можно в теле» (по умолчанию выключен), allowlist точных хостов и методы, список ботов. Значение пишет только владелец: POST в хранилище ОС, GET отдаёт метаданные и «задан» / «не задан». Allowlist и ботов меняет только это окно (CSRF, Origin, `isWrite`, Н59). `config.yaml` и `POST /api/bots/tools` эти поля не принимают. Удаления нет.
- Бот видит `{{secret:NAME}}` и описание. Значение не входит в промпт и не уходит провайдеру модели. В ответе, предложении, брифе, записке, журнале, `chats/*.json` и proposals ссылка и значение заменяются на `[secret]`.
- Инструмент один: `http_request`. Фиксированных команд нет. Подстановка один раз, без второго прохода. Только в заголовок карточки; в тело — если флаг включён. В URL, пути и query — отказ. Неизвестное имя и бот не из списка — отказ.
- Allowlist: точный хост в punycode, без `*.`, только `https` и порт 443, список методов. `https://user@host` отвергается. Редирект не выполняется. После DNS частный, loopback и link-local адрес, включая `169.254.169.254`, отвергается. Соединение открывается к уже проверенному IP.
- Ответ боту маскирует значение короче 8 символов не трогая, а начиная с 8 — буквально, в base64 (включая Basic `user:pass`), URL-encoding, hex и JSON-escape, в том числе если оно разрезано между частями ответа. Ответ длиннее 64 КиБ обрывается. Журнал `data_dir/secrets/journal.jsonl` хранит имя, хост, метод и статус, без значения. Один ключ — не больше 10 вызовов за 60 с.
- Значение из хранилища в `process.env` не кладётся. Дочерние процессы получают узкое окружение: процесс связки (Н102), git, открытие браузера и проверка папки. `secret:set` без `--replace` проверяет связку до скрытого ввода (Н103).
- В `.gitignore`: `.env`, `config.yaml`, `data/`, `node_modules/`, `dist/`, `*.log`, `.DS_Store`.
- Перед коммитом запускается проверка pre-commit (gitleaks или аналог). В CI тоже: gitleaks, наличие `LICENSE` и `NOTICE`, grep по запрещённым реальным именам и путям (список из 3.7).

### 3.7 Что в v6 захардкожено и должно уйти в конфиг или демо
- **Боты:** имена, роли, короны главных, статусы и пауза. CSS-маскоты и PNG-аватар. В макете и в `demo/` только вымышленные имена.

- **Владелец:** отображаемое имя и инициалы в рейле. В демо владелец — Alex. Открытые вопросы в документе адресованы владельцу, без реального имени.
- **Направления:** названия чатов и их правила. В демо: Сборка, Оформление, Проверка, Анонсы, Витрина.
- **Данные:** пути к исходникам, номера запросов, короткие SHA, имена веток, тексты задач и чата. В демо — относительные пути вроде `src/app.txt` и плейсхолдеры `<repo>`, `<data_dir>`, `<files_root>`, `<bot-id>`.
- **Прочее:** время с чужой зоной (в интерфейсе зона берётся из конфига), счётчик «62%», лимит «короткий», правила проекта в тексте.

### 3.8 Контракт файлов `data_dir`
Форматы — `docs/CONTRACT.md`. Поля задачи и сдачи приведены к протоколу ревизора. Если `ARCH.md` §2 расходится (старые имена полей `brief`/`files`/`result`), действует `docs/CONTRACT.md`. Все файлы: `schema_version`, `updated_at` (ISO с зоной); валидация zod при чтении; невалидный файл — ошибка на карточке, сервер не падает.
- `tasks/<task_id>.yaml` — пишет главный: `id, project, chat, assignee, goal, inputs[]` (пути/SHA/PR), `output, done_when, out_of_scope, reply_limit, due, status(new|working|review|done|blocked), updated_at`.
- `status/<bot_id>.json` — пишет только исполнитель: `task_id, state(working|blocked|done), links[], verified, not_done, risks` (необязательное), `question_to_owner, updated_at`. Необязательная строка «риски» в сдаче; поле `risks` показывается в окне мержа (раунд 4).
- `merge_requests/<project>-<pr>.json` — пишет главный: модель §4.4 плюс `head_sha`, `history[{state,at,by,why}]`.
- `outbox/` — пишет только лаунчер: `decisions/<project>-<pr>.json` (`action`, `head_sha`, `by`, `at`; новый пуш с другим `head_sha` делает решение недействительным), `queue/<task_id>.yaml`, `feedback/<id>.json`.
- `usage/<неделя>.json` — снимок расхода, пишет главный раз в неделю или по кнопке; лаунчер после синка только читает и строит график (§7). Отдельная рутина не нужна.


## 4. Запрос на мерж

### 4.1 Кто что делает
- **Исполнитель** (бот направления) готовит изменения и сдаёт отчёт в `status/<bot>.json`.
- **Главный** в чате или проекте собирает запрос из ссылок на сдачи (без пересказа), привязывает его к задаче и пишет `merge_requests/<project>-<pr>.json`, затем пишет владельцу: «готов запрос на мерж» (`docs/CONTRACT.md`, `skill/team-token-economy.md`).
- **Лаунчер** показывает уведомление (бейдж и тост) и модалку.
- **Владелец** (`owner`, единственный, кто подтверждает мерж; во всех наших проектах это владелец) выбирает «Смержить», «На доработку» или «Отклонить». Отзыв уходит в выбранные чаты. Решение лаунчер пишет в `outbox/decisions/`.
- **Исполнитель мержа** (`merge_executor` в конфиге проекта, по Demo Game это Бит) стартует **только** из состояния `delivered`. Лаунчер ставит `approved`; `delivered` ставит только главный после синка. Бриф «мержи <id>» доставляется тем же способом, что и обычный (раздел 1).

### 4.2 Модалка запроса
Разделы: **Что сделано** · **Что не работает** · **Что перенесено** · **Риски** · **Затронутые направления** · **Ссылки** (PR, CI, diff) · **Прочее для решения**. Порядок на экране и липкий низ — §10 п. 1 и `docs/UI_SPEC.md`.
Мерж привязан к задаче (раунд 3). Если задача шла в одном чате, мержится и уведомляется только этот чат. Перед мержем лаунчер проверяет расхождения: если другой чат затронул те же код, файлы или документацию, это показывается в окне мержа. Необязательное поле `risks` из сдачи показывается в разделе «Риски» (раунд 4).
Кнопки: **Смержить**, **На доработку**, **Отклонить**. Комментарий обязателен для «На доработку» и «Отклонить». «Смержить» неактивна, пока CI красный, но владелец может принять осознанно, отметив «принимаю риск».

### 4.3 Итерации
После доработки исполнитель создаёт повторный запрос с тем же `id` и номером итерации +1. В модалке видна история по каждой итерации:
**что не нравилось** (цитата отзыва) → **что исправлено** → **что осталось**.

### 4.4 Модель данных
```json
{
  "id": "mr-2026-11-19-001",
  "project": "demo-game",
  "task_id": "…",
  "mode": "git | files",
  "head_sha": "...",
  "status": "draft | awaiting_owner | changes_requested | approved | delivered | merging | merged | rejected | merge_failed | reverted",
  "author": "dev1", "lead": "lead1", "merge_executor": "dev1", "owner": "owner",
  "affected_chats": ["dev", "design"],
  "links": { "pr": "...", "ci": "...", "diff": "..." },
  "iterations": [
    {
      "n": 1, "created_at": "2026-11-19T13:00:00+03:00",
      "done": ["..."], "broken": ["..."], "postponed": ["..."], "risks": ["..."], "other": "...",
      "addressed_feedback": null,
      "decision": {
        "by": "owner", "at": "...", "action": "changes_requested",
        "feedback": "текст отзыва", "sent_to_chats": ["dev", "design"]
      }
    },
    {
      "n": 2, "addressed_feedback": { "quote": "текст отзыва", "fixed": ["..."], "remaining": ["..."] },
      "decision": null
    }
  ],
  "history": [{ "state": "awaiting_owner", "at": "...", "by": "lead1", "why": "..." }],
  "merge": { "commit": null, "executed_by": null, "at": null },
  "revert": { "pr": null, "requested_by": null, "approved_by": null }
}
```

### 4.5 Состояния
Единый автомат — `docs/CONTRACT.md` (ARCH.md §3 на него ссылается и с ним не спорит):

`draft → awaiting_owner → (changes_requested → awaiting_owner …) → approved → delivered → merging → merged`.

Другие исходы: `→ rejected` · `merging → merge_failed → awaiting_owner` · `merged → reverted`.

- Лаунчер ставит `approved`. Состояние `delivered` («решение доставлено на бокс») ставит только главный после синка. `merge_executor` стартует только из `delivered`.
- Если `head_sha` изменился после `approved` — запрос возвращается в `awaiting_owner` (решение было привязано к старому SHA).
- Каждый переход пишется в `history[{state,at,by,why}]`.

### 4.6 Выполнение
- **git:** исполнитель мержит PR через свой коннектор, без force-push. В запрос пишутся SHA и CI. Откат идёт **только через revert-PR**, и его тоже подтверждает владелец (тот же флоу с `mode: revert`).
- **files** (проект без git): diff и PR нет. В запросе список изменённых файлов с размером и временем и превью текстовых файлов «было/стало», если исполнитель сохранил копии. «Смержить» означает «принять изменения в файлах»: исполнитель переносит файлы из рабочей папки (`staging/`) в основную. Перед заменой он делает снимок `backups/<mr-id>/`. Откат — восстановление из снимка (сверка sha256 с исходными), тоже с подтверждения владельца.

## 5. Источники Git и файлов
- **git-проекты:** сервер читает GitHub API с read-only токеном из `.env` и отдаёт фронту агрегаты: коммиты, diffstat, PR, CI. Патч файла в ответ не копируется. Токен в конфиг не подмешивается и во фронт не попадает. Реализация — `docs/ARCH.md` §11.
- **Без git:** вкладка Git скрыта, «Файлы» показывают дерево папки из `source.files.path`, мерж идёт в режиме `files`.
- **Решение для нашей инсталляции:** Demo Files (<files_root>) пока без git, `git init` не делаем. Вкладка Git для Demo Files скрыта, данные берутся из файлов <files_root>.
- Граф связей строится из разметки «файл → отвечает за» в конфиге или `docs/`. Автоматический разбор кода — потом.

## 7. Общий скилл экономии токенов `team-token-economy`

Протокол и правила: `skill/team-token-economy.md`. Форматы файлов: `docs/CONTRACT.md`.

### Протокол
1. Бриф принимает только `lead` проекта (§1) и режет на карточки `tasks/<id>.yaml`. Других ботов не будят.
2. **Задача**, не больше 8 строк: `id · исполнитель · цель · вход (пути, SHA, PR) · done_when · вне объёма · reply_limit · срок`. Истории чата и пересказа плана нет, только ссылки на § и пути.
3. **Сдача** в `status/<bot>.json`, не больше 6 строк: `id · done|blocked · ссылки · что проверено · не сделано/отложено · вопрос владельцу`. Необязательная строка «риски» (поле `risks`) показывается в окне мержа. В чат идёт одна строка «id готово/blocked», и только если ждёт главный.
4. **Ревью**, не больше 6 строк: `APPROVE|REQUEST CHANGES · блокеры B1..Bn (файл:строка) · неблокирующие одной строкой`.
5. **Мерж.** Главный собирает запрос (§4.4) из ссылок на сдачи, без пересказа. Владелец апрувит, `merge_executor` мержит из `delivered` (§4.5).

Правила протокола:
1. Исполнитель получает только карточку задачи и файлы своего направления (`directions[].paths`). Общий контекст — путём к файлу, без пересказа чата.
2. Главный не пересказывает чужой результат, передаёт ссылку. Итог владельцу — один пост.
3. Ревью смотрит diff и то, что от него зависит. Полная сверка бывает только на вехах.
4. «Пауза»/«стоп» сразу останавливает фоновые задачи бота, новых не запускать до «продолжить». Повторные пробуждения на ту же задачу ограничены: `max_wakes_per_task` по умолчанию 3; после лимита задача уходит в `blocked` и возвращается владельцу.
5. Отдельных сообщений «принял» и «готово» нет, вместо них обновляется записка о статусе.

### Базовые предустановленные правила (утверждены владельцем)
Источник: `skill/team-token-economy.md`, раздел «Базовые правила» (`rules.base`, включены всегда).
1. В комнате каждое сообщение будит всех. Пишем только итог в одну строку или вопрос для всех; вопрос одному боту — лично. Нечего добавить — молчим, без «принял» и «спасибо».
2. Рутины только по нужде: раз в день или по кнопке, при «ничего не изменилось» — без сообщения.
3. Задача ставится одним полным брифом (цель, входные файлы, критерий готовности), не цепочкой уточнений.
4. У каждого вопроса один ответственный; роли не дублируем, чужую часть не проверяем и не пересказываем.
5. Большие файлы читаем выборочно; в сообщениях — путь и раздел (§, строки), не копия текста.
6. Развёрнутый ответ даётся только когда это действительно нужно (план, отчёт, разбор или прямая просьба пользователя); во всех остальных случаях ответ короткий.


Настраиваемые правила (`rules.defaults`, всё меняется в конфиге, кроме `rules.base`) — таблица в `skill/team-token-economy.md`. Лимиты (раунд 4): `reply_limit` 6 строк, `brief_limit` 8 строк, `max_wakes_per_task` 3. Правило развёрнутого ответа — в `rules.base` выше.

### Очередь (правило 8а)
По умолчанию выключена. Если включена, запуск не чаще раза в день по cron или по кнопке. Когда очередь пуста, рутина выходит **без сообщения** в чат (не строкой «пусто»): сообщение будит людей. Синк одним бандлом `.tgz` выполняется в том же ходе, что и разбор очереди, и только если есть изменения (сверка sha256 манифеста). Если за 7 дней в очереди не было ни одной задачи, лаунчер предлагает выключить рутину.

### Замер (п. 9) и статистика расхода
Фиксированной цели экономии в 30% нет (раунд 3). В интерфейсе — график последних 7 недель и примерный процент сэкономленного.

Статистика Grok Bot хранится не больше 30 дней, API для неё у лаунчера нет. Раз в неделю главный бот пишет снимок в `data/usage/<неделя>.json`. После синка лаунчер только читает эти снимки и строит по ним график за 7 недель. Модуль `store` для снимков в `ARCH.md` добавит Бит (сам ARCH пока не меняем). Снимок делается по кнопке или в рамках уже существующей ежедневной работы, отдельная рутина не нужна. График заполняется постепенно: первый снимок может подтянуть до 4 недель из 30-дневной истории. Процент экономии — оценка; неделя до внедрения правил идёт как база для сравнения.

Счётчик в шапке тоже оценка (пробуждения на задачу, строки ответа, число повторов). Метрики в лаунчере: пробуждений на задачу, доля ответов сверх лимита, доля задач в `blocked`. Шаблоны карточки и сдачи в CI проверяются zod-схемами из `packages/schema`.

## 8. Риски

| Риск | Мера |
|---|---|
| Мерж или откат без владельца | Только флоу из раздела 4. Исполнитель мержит после `delivered` (главный поставил его после синка решения владельца) и брифа «мержи». Откат через revert-PR или снимок, тоже с подтверждением. Удаление фич только с одобрения владельца. |
| Утечка секретов в публичный репо | `.env` и `config.yaml` в `.gitignore`, gitleaks в pre-commit и CI, только демо-данные. Сервер слушает только `127.0.0.1`, проверка `Host`/`Origin` и CSRF, файлы только внутри путей из конфига. |
| Записки устарели или не записаны | Метка «обновлено ЧЧ:ММ», серый цвет и иконка часов. Главный помечает задачу «нет записки» и не будит бота повторно без решения владельца. |
| Гонки при записи | Один писатель на файл, атомарная запись через tmp и rename. |
| Рутина доставки дорого стоит | По умолчанию `clipboard`. Рутина включается явно, раз в день или по кнопке; пустая очередь молчит. Расход — по доле рутин в статистике. |
| Ссылка `grokbot://` не открывается из браузера | Рядом со ссылкой всегда имя бота и «Если чат не открылся, откройте <имя> вручную» (техпроверка 1, §12). |
| Расхождение бокса и ПК | Один писатель на каждую сторону (боты пишут на бокс, лаунчер в `outbox/` на ПК). Синхронизирует главный бот одним бандлом `.tgz` в каждую сторону. Метка «данные на ЧЧ:ММ». Решение по мержу не действует, пока нет `delivered`. Смена `head_sha` после `approved` возвращает запрос владельцу. |

## 9. Визуальные эффекты

**Видео-референс (2026-11-19):** разбор в `docs/UI_SPEC.md`. Берём эффекты 1–4 и 7 (`UI_SPEC.md` §4.1): линия появляется только во время обмена, по ней бегут частицы, активный бот пульсирует, рядом всплывает карточка задачи, счётчики меняются плавно. Фоновые частицы и режим «все сразу» не берём. `v6.html` остаётся статичным эталоном для сравнения снимков.
Только `transform` и `opacity`, 150–300 мс. При `prefers-reduced-motion: reduce` всё отключается. Невидимые анимации стоят на паузе.
- Орбита: «дыхание» маскотов, пунктир от главного к адресату, кольцо-вспышка вокруг разбуженного бота.
- Карточка бота выезжает оверлеем, а не перестраивает орбиту.
- Канбан: перенос карточек через FLIP. Счётчик дотикивает.
- Запрос на мерж: тост и бейдж. Модалка поднимается снизу с fade. После «Смержить» короткая галочка, после «На доработку» карточка возвращается в «В работе».
- Фон статичный, анимированного blur нет.

## 10. Доработки макета v6
1. **Новая модалка «Запрос на мерж»**: семь разделов, поле отзыва, выбор чатов с предвыбором, кнопки «Смержить», «На доработку», «Отклонить», «принимаю риск» при красном CI. Порядок сверху вниз (`docs/UI_SPEC.md`): заголовок + исполнитель + ссылка (PR/папка); что сделано; что не работает; отложено; риски; CI / проверки; итерации (лента «отзыв → исправлено → осталось»). Низ липкий: поле отзыва, чипы «кому отправить отзыв», кнопки слева направо `Отклонить` (текст) · `На доработку` (вторичная) · `Смержить` (главная, тёмная). Красный CI: «Смержить» неактивна, чекбокс «принимаю риск» включает её. После «Смержить» — галочка и тост; запрос уходит в историю.
2. **Новые экраны истории:** лента итераций запроса (цитата отзыва → исправлено → осталось), список всех запросов проекта со статусами, история мержей и откатов.
3. **Шапка:** «Смержить» превращается в «Запросы на мерж (N)». «Откатить» открывает запрос на revert. Обе кнопки неактивны без подходящих объектов и объясняют почему.
4. **Бриф:** «Скопировать бриф» с превью, рядом «Открыть чат главного» (`grokbot://`) и всегда подсказка «Если чат не открылся, откройте <имя> вручную», плюс кому уйдёт бриф. В шапке «данные на ЧЧ:ММ» и «Синхронизировать».
5. **Настройки чата:** выбор главного с наследованием «как в проекте», лимит ответа (короткий, средний, полный), пауза участника, `delivery`. При расхождении правил чата и проекта — запрос пользователю, без автоматического приоритета (раунд 3).
6. **Настройки проекта:** владелец, исполнитель мержа, источник git или файлы, переключатель «нет git — скрыть Git», проверки по расписанию (по умолчанию выкл.). В настройках лаунчера — бот недельного аудита протокола (раунд 3).
7. **Мастер настройки** и пустые состояния (нет проектов, нет ботов).
8. **Файлы:** отступы дерева (`README.md` и `ACCEPTANCE.md` правее `docs/`), подписи рёбер графа, подсветка выбранного узла. Сделано в этапе 3, проверка — e2e со скриншотом.
9. Карточку «Витрина — нет активного модуля» убрать из канбана. Вкладку «Чат», которая дублирует правую панель, убрать. Неиспользуемые направления свернуть.
10. Подсказка к счётчику («оценка»). Время с зоной из конфига. Брейкпоинты 1280 и 1920 (сейчас `@media` нет). Свои шрифты вместо `local()`. Видимый фокус, alt у маскотов, контраст `--faint` по AA.
11. Весь хардкод из 3.7 заменить на демо-данные.
12. Счётчик в шапке подписать «экономия ≈62% (оценка)» + тултип, как считается. Тумблер отдельно от полоски.
13. Над полем ввода чип «проснётся: <бот>» и выбор лимита ответа; при @упоминании чип меняется сразу.
14. Колонка «На проверке» связана с «Запросами на мерж (N)»: на карточке кнопка «Открыть запрос» и бейдж CI, мерж можно запустить из карточки.
15. Записка о статусе на карточке бота и канбана: «обновлено ЧЧ:ММ»; старше порога — серым и иконкой часов.
16. Орбита до 10 ботов; больше — переключатель «Орбита / Список». Подписи на орбите не перекрывают линии. Если ботов 10 или больше, при первом открытии показывается «Список», дальше запоминается последний выбранный вид (раунд 4).
17. Вопрос к владельцу — единый компонент (жёлтая плашка + «Ответить») в карточке бота, в чате и в счётчике шапки «Вопросы (N)».
18. Модалка настроек: длинную разбить на вкладки «Основное / Правила / Экономия / Уведомления», футер липкий.

**Состояния экранов** (для каждого: пусто / загрузка / ошибка / устарело) — таблица в `docs/UI_SPEC.md`: рейл и орбита ведут в мастер; бот без записки — серый, без пульса; канбан при устаревших данных — «данные на ЧЧ:ММ» + «Синхронизировать»; нет git — вкладка скрыта (§5); сбой доставки брифа — «Скопировать бриф»; красный CI блокирует «Смержить» до «принимаю риск».

**Токены и вёрстка.** Источник — `UI_SPEC.md` (токены, компоненты, состояния, брейкпоинты 1280/1920, фокус и AA). Вид списком при 10+ ботах — кадр `v6-list.png`. Отличие от v6 не больше 2% пикселей считается совпадением (раунд 4). **Тёмная тема** входит в v1 (раунд 3).

## 11. Вопросы владельцу

Все пункты решены (раунды 3 и 4, 2026-11-19).

1. **Линт.** Разрешить тестовую рутину для техпроверок 2 и 3 (§12)? **Решено (раунд 3):** тестовую рутину не заводим. Техпроверки 2 и 3 делаем вручную по кнопке. Проверки по расписанию настраиваются в каждом проекте; по умолчанию автоматизации нет.
2. **Пикс.** Тёмная тема лаунчера нужна в v1? **Решено (раунд 3):** да, тёмная тема сразу, в v1.
3. **Пикс.** Порог «устаревшей» записки? **Решено (раунд 4):** записка становится серой через 6 часов, порог настраивается в проекте.
4. **Рев.** Лимиты `reply_limit` 6, `brief_limit` 8, `max_wakes_per_task` 3? **Решено (раунд 4):** да. Развёрнутый ответ — только когда это действительно нужно (план, отчёт, разбор или прямая просьба пользователя); иначе ответ короткий. Правило внесено в §7 и `rules.base`.
5. **Рев.** Если правила чата и проекта расходятся, какие главнее? **Решено (раунд 3):** автоматического приоритета нет. Лаунчер показывает запрос о расхождении, решает пользователь.
6. **Тэст** (`ACCEPTANCE.md` E1). Порог отличия от v6? **Решено (раунд 4):** если вёрстка отличается не больше чем на 2% пикселей, это считается совпадением.
7. **Тэст** (`ACCEPTANCE.md` F9). Цель экономии минус 30%? **Решено (раунд 3):** фиксированной цели в 30% нет. В статистике — последние 7 недель и примерный процент сэкономленного (§7).
8. **Из `ACCEPTANCE.md` D5.** Где мерить fps орбиты? **Решено (раунд 4):** плавность проверяет автотест (в CI не ниже 55 fps). От владельца здесь ничего не требуется.
9. **Из `ACCEPTANCE.md` F4–F6.** Кто ведёт недельный аудит протокола? **Решено (раунд 3):** бот, выбранный в лаунчере (настройка).
10. **Противоречие §4.2 и Пикс.** Кого предвыбирать в чипах отзыва? **Решено (раунд 3):** мерж привязан к задаче. Если задача шла в одном чате, мержится и уведомляется только этот чат. Пересечения с другими чатами показываются в окне мержа.
11. **Противоречие Рев и Бит.** Добавить `risks` в схему? **Решено (раунд 4):** в формат сдачи добавляется необязательная строка «риски», в схему — поле `risks`. Поле показывается в окне мержа.
12. **Пикс.** Вид при 10+ ботах? **Решено (раунд 4):** если ботов 10 или больше, при первом открытии показывается «Список», дальше запоминается последний выбранный вид.

## 12. Техпроверки (этапы 0–1)

Источник и способы: `docs/lint.md`. Все три пока не проверены.

1. **Открывается ли `grokbot://` из браузера на ПК.** Как проверить: Владелец вставляет `grokbot://app/v1/agent?id=<bot-id>` в адресную строку Chrome на ПК. Если не откроется — в UI запасной вариант: копируем бриф и называем бота.
2. **Держится ли апрув доступа к ПК при действии без участия человека.** Ожидание: действия внутри `<files_root>/` проходят по сохранённому правилу без карточки, остальные ждут апрува и могут истечь, если владельца нет. Как проверить: вручную по кнопке (тестовую рутину не заводим); кнопка инициирует запись `<data_dir>/ping.txt`.
3. **Сколько стоит запуск очереди.** Заранее назвать цифру нельзя: статистика Grok Bot хранится не больше 30 дней и показывает долю каждой рутины в общем расходе, расхода по сообщениям нет; API у лаунчера нет. Как проверить: 2–3 дня запускаем очередь вручную по кнопке «Отправить очередь» (не чаще раза в день), затем смотрим долю в статистике и в снимках `usage/`.
