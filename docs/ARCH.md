# TinyBots — архитектура и стек (19.11.2026)

Стек, который уже в дереве: Node 20 LTS + TypeScript strict, Hono, Vite + React, zod, yaml. chokidar и SSE — позже. Вкладка Git читает GitHub через `fetch`, без simple-git и без Octokit. Ниже — что добавить/уточнить.

## 1. Раскладка (npm workspaces, один `package.json` в корне)
```
packages/schema/   # zod-схемы: config, task, status, merge_request, outbox, sync_manifest
                   # → генерация JSON Schema в schema/ (один источник правды, типы общие для server и web)
server/            # Hono на 127.0.0.1
  config/          # загрузка и валидация config.yaml. Мастер и подмешивание .env — позже
  store/           # data_dir: чтение, атомарная запись (tmp+rename). Блокировка одного писателя и chokidar → SSE — позже
                   #   usage/<YYYY-Www>.json — недельный снимок расхода пишет главный бот (статистика Grok Bot ≤30 дней), лаунчер только читает и строит график за 7 недель
  tasks/           # очередь задач, статусы, «устарело» по stale_after_hours
  merge/           # конечный автомат мержа (ниже)
  briefs/          # шаблоны брифов (≤ 8 строк) из задачи + конфиг чата; «Скопировать» / grokbot://
  sync/            # манифест и бандлы для главного бота (ниже)
  git/             # fetch к GitHub API. Токен только для чтения из .env, во фронт не попадает
  files/           # дерево и граф файлов проекта (только чтение, по allowlist путей из конфига)
  api/             # роуты /api/*. SSE /api/events — позже
web/               # перенос v6 в компоненты. TanStack Query и инвалидация по SSE — позже
demo/              # вымышленные данные, на них же e2e-тесты
```
БД нет: всё — файлы в `data_dir` (их же синхронизирует главный бот). SQLite — только если появится история/статистика больше одного экрана.

## 2. Форматы в data_dir (машиночитаемые, для экономии токенов)
- `tasks/<task_id>.yaml` — одна задача = один файл: `id, project, chat, assignee, brief(≤8 строк), files[], done_when, reply_limit, status, pr, updated_at`. Боты ссылаются на id, а не пересказывают.
- `status/<bot_id>.json` — записка бота: `task_id, state(working|blocked|done), result(≤6 строк), links[], updated_at`. Один писатель — сам бот.
- `merge_requests/<project>-<pr>.json` — от исполнителя.
- `outbox/` — только лаунчер: `decisions/`, `queue/`, `feedback/`.
Все файлы валидируются zod при чтении; невалидный файл показывается как ошибка карточки, а не роняет сервер.

## 3. Конечный автомат мержа
Единый вариант — см. docs/CONTRACT.md «Автомат мержа» (§4.5 плана + состояние `delivered`).

## 4. Синхронизация бокс ↔ ПК (меньше одобрений и токенов)
- Вместо пофайлового копирования — **по одному бандлу в каждую сторону**: `sync/box-to-pc.tgz` (status, merge_requests, tasks) и `sync/pc-to-box.tgz` (outbox). Итого 2 операции с ПК на синхронизацию, а не N.
- В бандле `sync_manifest.json` (путь, sha256, updated_at); распаковка пропускает неизменённые файлы и не перезаписывает файлы другой стороны (правило «один писатель»).
- Лаунчер сам собирает `pc-to-box.tgz` и сам распаковывает входящий — главному боту остаются ровно две команды копирования и одна строка в ответе.

## 5. Безопасность локального сервера
- Слушать только `127.0.0.1`; проверка заголовков `Host`/`Origin` (защита от DNS rebinding) и CSRF-токен на все записывающие роуты.
- Доступ к файлам — только внутри путей из конфига (нормализация, запрет `..` и симлинков наружу).
- Секреты только из `.env`, в API и логи не попадают; gitleaks в pre-commit и CI.

## 6. Качество и CI
`tsc --strict`, eslint, vitest (схемы, автомат мержа, атомарная запись, синк-манифест), Playwright на demo-данных (основные экраны v6, мастер, флоу мержа), проверка LICENSE/NOTICE, gitleaks. Кросс-ОС матрица: windows-latest + ubuntu-latest.

## 8. Пульт чтения (этап 1, критерии B1–B4 и B12–B16)

Сервер читает `config.yaml` схемами `@tinybots/schema`. Порядок выбора файла: аргумент запуска, `TINYBOTS_CONFIG`, `config.yaml`, иначе `demo/sets/primary/config.yaml`. `data_dir` считается от папки конфига. Битый YAML или схема не роняют процесс: `GET /api/launcher` (и соседние маршруты проектов, состава, чатов, записок, задач, синка) отвечает `422` с `file`, `line`, `reason`.

Записка — `data_dir/status/<bot_id>.json`. Нет файла или файл не проходит схему: в ответе `status: missing|broken`, на экране «нет записки». Старше `stale_after_hours` относительно часов запроса — `stale: true`. Метка шапки — самый поздний `updated_at` валидных `sync/*.json`, подпись `ЧЧ:ММ` в `timezone` конфига (нет поля — UTC).

Запись на диск — `writeAtomic` (временный файл рядом и `rename`, повтор при EPERM и EBUSY). Записывающие маршруты: `POST /api/setup`, `POST /api/merge/decide`, `POST /api/sync/apply`. Они стоят в одной очереди. Порт Host/Origin проверяет тот же `requestAllowed`, что и чтение. Нет заголовка Origin или он пустой — чтение пускает (так открывают страницу), запись отвечает 403. Строка `null` — не пустой заголовок: `requestAllowed` отклоняет её и на чтении, и на записи, потому что это не адрес `http://127.0.0.1`. Токен берётся с `GET /api/launcher` и с `GET /api/setup`. Тело проходит zod до записи. Новый `config.yaml` публикуется целиком: полный текст во временном файле, затем `link` на цель. Пустого файла при обрыве до `link` не остаётся. Если цель уже есть и она не пустая, без `confirm_overwrite` ответ 409. Пустой или из одних пробелов файл мастер считает незаписанным (`required: true`, `exists: false`) и заменяет. Параллельные POST идут по очереди: один ответ 200, остальные 409. `demo/` и `config.example.yaml` не перезаписываются. `data_dir` остаётся относительным путём внутри репозитория и не может быть `.git`, `package.json`, `node_modules`, `.github`, `scripts` или устройством Windows (CON, NUL, PRN, AUX, COM1–9, LPT1–9), в любом регистре, с расширением и с хвостовыми точками или пробелами. Управляющие символы U+0000…U+001F в `data_dir` отвергаются до разбора сегментов. Папка проекта (`source.files.path`) может лежать где угодно, в том числе вне лаунчера; запрет на управляющие символы, UNC (`\\server\share`, `//server`, смешанные `\/` и `/\`) и device-пути (`\\?\`, `\\.\`). `GET /api/setup/source` требует токен до диска и git. Чужой Origin, строка `null`, чужой порт и чужой Host — 403. У GET с той же страницы заголовка Origin нет, его пускает только токен. `safe.directory=*` нет. `/` и `/setup` отдают `X-Frame-Options: DENY` и `Content-Security-Policy: frame-ancestors 'none'`. `/health` эти заголовки не ставит. Остальные не-GET отвечают 405. SSE — отдельно, когда появится подписка на файлы.

Страница (`apps/web`) тёмная, сетка как у v6: рейл, чаты, орбита, карточка, Задания, Канбан, Правила. Данные только из `/api/launcher`. Нет своего `config.yaml` или файл пустой — корень открывает мастер (семь шагов: владелец, боты, проект, чаты, источник, доставка, экономия). Демо остаётся по `?demo=1`. Пустые проекты, боты и записки ведут на `/setup`. Карточка бота — колонка справа от орбиты, не оверлей поверх правого узла: узел остаётся под курсором. Бриф — раздел 9. Запрос на мерж — раздел 10. Вкладки Git/Файлы/Документация и эффекты орбиты в этот срез не входят.

Команды: `npm test`, `npm run build -w @tinybots/web`, `npm run e2e`. Подмена часов для e2e — только `e2e/boot.mjs` (`TINYBOTS_NOW`), `npm start` её не читает. CI ставит Chromium пакетом `@playwright/test` 1.65: на Ubuntu `npx playwright install --with-deps chromium`, на Windows без `--with-deps`. Браузеры остаются в штатном кэше вне репозитория и кэшируются Actions по `package-lock.json`.

## 9. Бриф и доставка (этап 1, критерии B5–B11)

`GET /api/brief?project&chat&task` собирает текст из карточки задачи. Адресат: главный чата, а если такого бота нет — главный проекта. Главный на паузе или оба id пустые — ответ без текста, с просьбой выбрать главного. В тексте не больше 8 строк: что, зачем, файлы, критерий готовности, лимит ответа. История чата не подставляется.

«Скопировать бриф» кладёт в буфер текст превью. «Открыть чат главного» — ссылка `grokbot://app/v1/agent?id=<id>`, когда id проходит проверку формата. Рядом со ссылкой всегда «Если чат не открылся, откройте <имя> вручную». Пустой или битый id — та же подсказка, без ссылки.

`delivery: clipboard` в примере и демо. `queue` планировщик пускает не чаще одного календарного дня в зоне конфига; кнопка и расписание делят этот слот. Файл очереди этот срез не пишет.

## 10. Запрос на мерж (этап 2, критерии C1–C13)

Кнопка «Запросы на мерж (N)» считает запросы проекта в `awaiting_owner`. «Откатить» — запросы в `merged`. Нет таких объектов — кнопка неактивна, рядом текст почему.

Решение владельца пишет только `outbox/`. `POST /api/merge/decide` не меняет `merge_requests/*.json`. Кто решает, сервер берёт из `mr.owner` или `project.owner`, не из тела. `changes_requested` — не действие файла решения: это `outbox/feedback` с `intent: changes_requested`. «На доработку» и «Отклонить» без текста — 422. Красный CI без `accept_risk: true` не даёт `approved`.

`POST /api/sync/apply` доставляет outbox. Живого бота в этом срезе нет, поэтому один вызов на демо проходит цепочку, которую иначе разделили бы главный и исполнитель: `awaiting_owner` + `approved` от владельца → `approved` → `delivered` → `merging` → `merged` (или `merge_failed` → снова `awaiting_owner`, текст ошибки в `history`). Бриф `мержи <id> <pr_url>` собирается только в `delivered`, при `decision.action=approved` и `decision.by == owner`. Откат — бриф `откати <id> <pr_url>`, `mode: revert` только внутри брифа, из `merged`, тоже только от владельца. Пока синхронизации не было, статус на диске прежний.

GitHub — мок в `apps/server/src/merge/github-mock.ts`. Сети и токена нет. `pr_url` с `/mock-fail/` возвращает ошибку. Режим `files`: живой файл в папке проекта, новое содержимое в `staging/`, снимок до замены в `backups/<mr-id>/`. Список файлов не включает `.git`, `backups/`, `staging/`, устройства Windows, NUL, «.» и пустые сегменты. Первый снимок не затирается. Откат копирует снимок обратно, а файл, которого не было, удаляет. Обрыв посреди копирования делает то же с уже заменённой частью.

«На доработку» на демо добавляет итерацию n+1: цитата = текст отзыва, исправлено = «исправлено по отзыву», осталось = «осталось проверить», затем снова `awaiting_owner`. Повторная доставка того же отзыва вторую итерацию не создаёт. Полный бандл `box-to-pc.tgz` по-прежнему заглушка.

## 11. Git, файлы и документация (этап 3, критерии D1–D8)

`GET /api/git?project=` читает GitHub обычным `fetch` (пакет Octokit не добавлен). Токен — `GITHUB_TOKEN` из окружения, база — `GITHUB_API_BASE` или `https://api.github.com`. Ответ: коммиты, diffstat, открытые PR и статусы CI. Тело коммита и патч файла в ответ не копируются. Токен запоминается и вырезается из логов и из ответа, если API вдруг его вернул. Права записи (`repo`, `repo:status`, `workflow`, `gist`, `user`, `write:`, `admin:`, `delete:` и соседние) — предупреждение, вкладка не стартует. `repo:status` пишет статусы коммитов, это не чтение. Нет заголовка scopes и нет объекта `permissions` из одних `read` — тоже не стартует: fine-grained токен без этих полей считается неизвестным. Классический токен после проверки прав открывает вкладку для публичных репозиториев. Токена нет — та же остановка, без сети. На всём `/api` заголовок `Sec-Fetch-Site` пускает только `same-origin`, `none` или отсутствие заголовка. `same-site` и `cross-site` отвечают 403 до вызова GitHub и до вызова модели.

`GET /api/files?project=` и `GET /api/docs?project=&path=` отдают только то, что лежит внутри `source.files.path` после `realpath`. `..`, абсолютный путь, UNC, двоеточие, симлинк внутри дерева — 404. Корень папки может быть симлинком: тюрьма — это его `realpath`. Документ — только `*.md` не длиннее 64 КиБ. Рёбра графа читаются из markdown вне ограждений: `from → to | подпись`.

Страница рисует markdown блоками React, без `dangerouslySetInnerHTML`. Движение — только `transform` и `opacity`, 150–300 мс. `prefers-reduced-motion: reduce` обнуляет длительности. Lighthouse и кадры орбиты — отдельный job CI, только Ubuntu и Node 24. Остаточный риск записи файлов: `docs/files-safety.md`.

## 12. Свои боты (критерии H1–H15)

Бот в конфиге — одна из двух строгих форм. Бот Grok Bot остаётся с необязательным `grok_id`. Свой бот несёт инструкции, провайдер, модель, `base_url` и `api_key_env`. Значения ключа в YAML нет. Имя переменной проходит `^[A-Z][A-Z0-9_]*_API_KEY$`, поэтому `GITHUB_TOKEN` и `PATH` не становятся ключом модели.

Вызов — `POST {base_url}/chat/completions` обычным `fetch`, `stream: false`, таймаут 60 с. 401 не повторяется. На 429 не больше трёх повторов, `Retry-After` не дольше 60 с. Тело больше 1 МиБ — ошибка, процесс жив. В системный текст входят роль, инструкции, `skill/team-token-economy.md` как `rules.base` и `reply_limit`. Чужой чат и тела файлов проекта не подставляются. Выключателя `rules.base` нет.

`base_url` — только `https`, кроме явного `http://127.0.0.1` и `http://localhost`. Числовые IPv4, `0.0.0.0`, частные и link-local адреса, `::1`, `fc00::/7`, `fe80::/10`, `::ffff:` на частный IPv4, а также IPv6 со встроенным IPv4 (`64:ff9b::/96`, `64:ff9b:1::/48`, `2002::/16`, `::/96`, `fec0::/10`, `::ffff:0:0:0/96`) отвергаются. `fetch` идёт с `redirect: 'manual'`, любой 3xx — ошибка. Перед запросом имя резолвится, и каждый адрес проходит те же правила. Остаточный риск: между `dns.lookup` и соединением резолвер ОС может вернуть другой адрес (окно TOCTOU). Закрепить IP без своего HTTP-агента этот срез не стал. Тесты и CI вызывают только локальный мок, без сети к провайдеру.

Ключ читается из `process.env[api_key_env]` после `loadDotEnv` и сразу попадает в `rememberSecret`. В `data_dir`, логи, ответы и git значение не пишется. Короткое значение по-прежнему не прячется.

История чата — `data_dir/chats/<bot_id>.json`, не больше 100 сообщений, запись через временный файл и `rename`. Битый файл не роняет процесс. Пробуждения задачи — `data_dir/wakes/<task_id>.json`. Четвёртое при лимите 3 переводит задачу в `blocked` и модель не вызывает. Параллельные ходы сериализуются на одном счётчике. `paused: true` вызовов не делает.

Ответ на бриф разбирается `statusSchema`. Невалидный JSON не затирает `status/<bot_id>.json`. Записка не ставит задаче `done`, не запускает мерж и не меняет `lead` или `assignee`. Расход — `data_dir/api-usage/<ИМЯ_ПЕРЕМЕННОЙ>.json` по полю `usage`. Нет `usage` — на экране «нет данных», оценка не пишется. Недельный `usage/<YYYY-Www>.json` не используется.

## 13. Инструменты папки и предложения (критерии I1–I18)

Свой бот читает `source.files.path`, только если `project_tools` не `off` и у проекта `allow_bot_tools: true`. Бот должен быть `lead` или участником чата. `respect_gitignore` по умолчанию `true`: читается только корневой `.gitignore`. Строки с `!`, `**` и непонятные шаблоны закрывают путь, а не открывают его.

Песочница переиспользует `requestAllowed`, `isMergeFilePath` и `isReservedDeviceName`. Имя сверяется дважды: как его попросили и как оно лежит на диске (`dev`/`ino`). Жёсткая ссылка (`nlink > 1`) не читается и не пишется: `realpath` не видит, что второй линк может быть вне корня. Между повторным `lstat` и `rename` окна `openat` нет — это остаточный риск, его же описывает `docs/files-safety.md`.

Ход — цикл «модель → инструмент → модель» внутри того же `withLlmLock`. Не больше 16 вызовов, 6 логических запросов, 256 КиБ вывода, 10 с на вызов и 180 с на ход. Ретраи 429 этот срок не продлевают. Вывод инструмента идёт ролью `tool` с пометкой, что это данные, не инструкция. В system prompt тел файлов нет. Записка разбирается только из итогового текста.

Предложение лежит в `data_dir/proposals/`, не в `staging/` проекта. Автомат: `proposed → applying → applied | conflict`, `proposed → rejected | conflict`, `applied → reverting → reverted | revert_conflict`. Это не автомат мержа. `proposals/` не входит в синк бокс↔ПК: бандл синка всё ещё заглушка.

В папке без каталога `.git` «Применить» заменяет файлы со снимком в `proposals/<id>/backup/`. В git-проекте сервер делает локальную ветку `tinybots/proposal-<id>` через plumbing (`read-tree`, `update-index`, `write-tree`, `commit-tree`, `update-ref`), без checkout и без пуша. Рабочее дерево, HEAD и индекс пользователя не меняются. Подкоманды и аргументы — белый список. Окружение собирается с нуля, `GIT_*` родителя не наследуются, `GIT_ALLOW_PROTOCOL=none`, `GIT_NO_LAZY_FETCH=1`. `core.hooksPath` смотрит в пустой каталог `data_dir`. Локальный `.git/config` git всё ещё читает; опасные ключи перекрыты `-c` в префиксе. `-c safe.directory` не передаётся. Нужен git не старше 2.45.1. Частичный клон, чужой владелец и вложенный репозиторий отклоняются. Владелец вливает ветку сам.
