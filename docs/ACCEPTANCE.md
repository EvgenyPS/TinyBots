# TinyBots: критерии приёмки

Автор: Тэст. Дата: 19.11.2026. Основа: `LAUNCHER_PLAN.md` (v2) и макет `v6.html`.
Каждый пункт проверяется тестом или ручным шагом и даёт pass или fail. Этап закрыт, когда все его пункты зелёные и владелец поставил ✅.
Тесты: юнит и интеграционные — vitest (server и web); e2e — Playwright (Chromium) на демо; визуальные — Playwright + pixelmatch против `v6-*.png`.

---

## A. Этап 0: каркас и контракт

| ID | Критерий | Как проверяем |
|---|---|---|
| A1 | `npm install && npm start` на чистой машине поднимает демо на `127.0.0.1` за ≤ 2 мин | CI-матрица windows-latest, macos-latest, ubuntu-latest: запуск, затем `GET /health` → 200 |
| A2 | Сервер не слушает `0.0.0.0` | тест: запрос на внешний IP хоста отклонён; в коде нет `listen` без хоста |
| A3 | Есть `LICENSE` (Apache-2.0) и `NOTICE` | шаг CI падает, если их нет |
| A4 | В репо нет секретов и реальных данных | gitleaks в pre-commit и CI; grep по стоп-листу из 3.7 (`scripts/forbidden.txt`: реальные имена, пути, id) находит 0 совпадений |
| A5 | JSON Schema для config, task, status и merge-request валидируют демо-данные, а намеренно битые примеры отклоняют | `schema/__tests__`: по 3 валидных и 3 невалидных примера на каждую схему |
| A6 | `config.example.yaml` проходит схему, без секретов и путей пользователя | тест + grep |
| A7 | `.gitignore` содержит `.env`, `config.yaml`, `data/`, `node_modules/`, `dist/`, `*.log` | тест читает файл |
| A8 | Скилл `skill/team-token-economy.md` на месте, все пункты §7 плана в нём есть | чек-лист ревью |

## B. Этап 1: пульт, бриф, записки

### B.1 Данные только из конфига
| ID | Критерий | Как проверяем |
|---|---|---|
| B1 | Рейл, чаты, орбита, карточка бота, Задания, Канбан и Правила строятся из `config.yaml` | e2e: подменяем конфиг на второй демо-набор, и UI показывает новые имена; ни одного из старых не видно |
| B2 | Пустые состояния: нет проектов, нет ботов, нет записок | e2e на трёх урезанных конфигах: есть понятный текст и кнопка «Настроить», без падения |
| B3 | Битый `config.yaml` (YAML-ошибка или нарушение схемы) | сервер не падает; UI показывает файл, строку и причину |
| B4 | Время показывается в зоне из конфига | e2e с двумя зонами |

### B.2 Бриф и доставка
| ID | Критерий | Как проверяем |
|---|---|---|
| B5 | Бриф собирается за ≤ 3 клика от экрана проекта | e2e считает клики |
| B6 | Адресат брифа — главный по правилу «главный в чате → главный в проекте». В UI видно, кому уйдёт бриф | юнит на резолвер (4 случая: есть в чате; нет в чате, есть в проекте; главный на паузе; главного нет), e2e на подпись |
| B7 | Главный на паузе или не задан | бриф не формируется молча: показывается ошибка и предложение выбрать главного |
| B8 | Бриф ≤ 8 строк и содержит поля: что, зачем, файлы, критерий готовности, лимит ответа. Истории чата в нём нет | юнит на генератор: длина, наличие полей, нет вставленных сообщений |
| B9 | «Скопировать бриф» кладёт в буфер ровно то, что в превью | e2e через clipboard API |
| B10 | «Открыть чат главного» открывает `grokbot://app/v1/agent?id=<grok_id>`. Если ссылка не сработала или `grok_id` пуст, показываем имя бота и подсказку | e2e: проверка href и фолбэка; ручной шаг на ПК владельца (тех. проверка 1 из §11) |
| B11 | `delivery: queue` по умолчанию выключена. Если включена, запуск не чаще 1 раза в сутки или по кнопке | юнит на планировщик: второй запуск в те же сутки отклонён |

### B.3 Записки и синхронизация
| ID | Критерий | Как проверяем |
|---|---|---|
| B12 | Записка бота видна на карточке и в орбите с временем | e2e на демо |
| B13 | Записка старше `stale_after_hours` серая и с пометкой «устарело» | юнит + e2e с подменой времени |
| B14 | Отсутствующая или битая записка | показывается «нет записки», UI не падает |
| B15 | Атомарная запись: при обрыве посередине файл остаётся прежним | тест: kill процесса во время записи (tmp + rename), файл валиден |
| B16 | Метка «данные на ЧЧ:ММ» в шапке совпадает со временем последней синхронизации | e2e |

### B.4 Мастер настройки
| ID | Критерий | Как проверяем |
|---|---|---|
| B17 | Без `config.yaml` открывается мастер. После прохода пишется валидный конфиг, и пульт открывается | e2e полного прохода |
| B18 | Мастер проверяет путь и доступ к git; если git нет, предупреждает «вкладка Git будет скрыта» | e2e на папке без `.git` |
| B19 | Новый пользователь настраивает свой проект за ≤ 10 минут | ручной прогон человеком, который не видел проект, с таймером; плюс e2e ≤ 2 мин |

## C. Этап 2: запрос на мерж

| ID | Критерий | Как проверяем |
|---|---|---|
| C1 | Полный цикл на демо: запрос → «На доработку» → итерация 2 → «Смержить» → merged → revert → reverted | e2e одним сценарием в режимах `git` (мок GitHub) и `files` |
| C2 | **Без решения владельца мерж невозможен.** Бриф «мержи <id>» формируется только при `decision.action=approved` и `decision.by == owner` | юнит: попытка из любого другого статуса или от не-владельца отклоняется |
| C3 | Переходы только по графу §4.5. Любой другой переход (например, `draft → merged`, `rejected → merging`) отклоняется | таблица всех пар статусов, тест на каждую |
| C4 | Каждый переход пишет: кто, когда, почему | юнит на журнал |
| C5 | «На доработку» и «Отклонить» без комментария недоступны | e2e |
| C6 | При красном CI «Смержить» неактивна, пока не отмечено «принимаю риск»; отметка сохраняется в решении | e2e + проверка JSON |
| C7 | Отзыв уходит в выбранные чаты. По умолчанию отмечены чаты затронутых направлений | e2e: предвыбор совпадает с `affected_chats`; `sent_to_chats` в JSON совпадает с отметками |
| C8 | В истории итераций видно: цитата отзыва → что исправлено → что осталось | e2e на итерации 2 |
| C9 | Режим `files`: перед заменой создаётся `backups/<mr-id>/`; откат восстанавливает файлы побайтно | интеграционный тест: sha256 до мержа и после отката совпадают |
| C10 | Откат тоже требует «да» владельца (`mode: revert`) | юнит как в C2 |
| C11 | `merge_failed → awaiting_owner`, ошибка видна владельцу | e2e с моком ошибки |
| C12 | Решение по мержу не действует, пока не доставлено (бокс и ПК) | интеграционный тест: решение в `outbox/` без синхронизации не меняет статус на боксе |
| C13 | Кнопки «Запросы на мерж (N)» и «Откатить» неактивны без подходящих объектов и объясняют почему | e2e |

| ID | Критерий | Как проверяем |
|---|---|---|
| E1 | Экраны проекта, чата, бота, файлов и модалки совпадают с `v6-*.png` | pixelmatch на демо-данных, порог ≤ 2% (стартовый, уточним после первого прогона); различия, которые план меняет намеренно (§10), исключены маской |
| E2 | Брейкпоинты 1280 и 1920 без горизонтального скролла и наложений | e2e на 1280×800, 1440×900, 1920×1080 |
| E3 | Видимый фокус на всех интерактивных элементах; навигация с клавиатуры по основному флоу (бриф, модалка мержа) | e2e с Tab; axe-core без ошибок уровня serious |
| E4 | Контраст по AA, включая `--faint` | axe-core + скрипт по токенам |
| E5 | У маскотов есть `alt`, шрифты свои, без `local()` | статическая проверка |
| E1a | Эффекты из `UI_SPEC.md` §4.1 (линии при обмене, частицы, пульс, всплывающая карточка, докрутка счётчиков) не ломают сравнение снимков | снимки E1 снимаются с `prefers-reduced-motion: reduce` и в состоянии покоя; эффекты проверяются отдельным e2e: линия и частицы появляются только во время обмена и исчезают после него, работают только через `transform` и `opacity` |
| E6 | Убраны карточка «Витрина — нет активного модуля» и дублирующая вкладка «Чат» | e2e |

## F. Протокол работы ботов и экономия токенов

Как бот ведёт себя в чате, лаунчер не контролирует. Поэтому проверяем две вещи: что генерирует лаунчер (автоматически) и как боты следуют скиллу (по выборке).

| ID | Критерий | Как проверяем |
|---|---|---|
| F1 | Бриф будит ровно одного бота (главного); остальные участники в нём не упомянуты | юнит на генератор: 0 упоминаний неглавных |
| F2 | Бриф ссылается на файлы, PR и SHA, а не вставляет содержимое: нет вставок > 3 строк кода или diff | юнит |
| F3 | Бриф «мержи <id>» — одна строка с id и ссылкой на запрос | юнит |
| F4 | Ответ бота по умолчанию ≤ 6 строк (`reply_limit: short`) | ручной аудит: 20 случайных ответов за неделю, ≥ 90% в лимите |
| F5 | На одну задачу не больше `max_wakes_per_task` пробуждений | аудит по истории чатов за неделю; цель — 0 нарушений |
| F6 | Нет сообщений «принял», «готово» без содержания: статус идёт через записку | аудит, цель — 0 |
| F7 | Боты на паузе не просыпаются | аудит + юнит на резолвер (B6) |
| F8 | Счётчик экономии подписан «оценка» и считается по формуле из docs | юнит на формулу, e2e на подсказку |
| F9 | Расход до и после: доля пробуждений на задачу и средняя длина ответа | baseline за неделю до внедрения скилла, повторный замер через неделю после; цель — минус 30% пробуждений (стартовая, решает владелец) |

## G. Безопасность и надёжность

| ID | Критерий | Как проверяем |
|---|---|---|
| G1 | API сервера не отдаёт файлы вне `data_dir` и `source.files.path` (`../`, абсолютные пути, симлинки) | интеграционные тесты на path traversal |
| G2 | Запросы с чужого Origin отклоняются (CSRF и DNS-rebinding для localhost) | тест с поддельными `Origin` и `Host` |
| G3 | Токен GitHub с правами записи — сервер предупреждает и не стартует Git-вкладку | тест с моком scopes |
| G4 | Логи не содержат токенов и содержимого `.env` | grep по логам e2e-прогона |
| G5 | Два процесса пишут один файл | второй писатель получает отказ (один писатель на файл) |
